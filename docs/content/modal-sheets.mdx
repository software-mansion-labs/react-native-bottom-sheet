# Modal sheets

`ModalBottomSheet` renders above other content with an optional scrim
(transparent by default).

```tsx
const [index, setIndex] = useState(0);
const insets = useSafeAreaInsets();
```

```tsx
<ModalBottomSheet
  index={index}
  onIndexChange={setIndex}
  surface={
    <View style={[StyleSheet.absoluteFill, { backgroundColor: 'white' }]} />
  }
>
  <View style={{ padding: 16, paddingBottom: insets.bottom + 16 }}>
    <Text>Sheet content</Text>
  </View>
</ModalBottomSheet>
```

## Scrim

Tapping the scrim collapses the sheet to the closed detent. Use `scrimColor` to
customize the scrim color:

```tsx
<ModalBottomSheet
  index={index}
  onIndexChange={setIndex}
  surface={/* ... */}
  scrimColor="rgba(0, 0, 0, 0.3)"
>
  {/* ... */}
</ModalBottomSheet>
```

By default, the scrim fades in as the sheet opens and then holds at full
opacity, so detents above the first share the same scrim. Use `scrimOpacities`
to control the opacity at each detent: It takes one value in 0–1 per detent,
indexed to match `detents`, and interpolates linearly as the sheet is dragged
between them. A shorter array reuses its last value for any remaining detents.

The default maps each detent to 0 when it is closed and 1 otherwise, so the
scrim is transparent at any closed detent and fully opaque at every open one.

To keep the scrim deepening across every detent, pass one value per detent:

```tsx
<ModalBottomSheet
  index={index}
  onIndexChange={setIndex}
  detents={[0, 300, 'content']}
  scrimColor="rgba(0, 0, 0, 0.3)"
  scrimOpacities={[0, 0.5, 1]}
  surface={/* ... */}
>
  {/* ... */}
</ModalBottomSheet>
```

## Portal presentation contexts

A portal's presentation context is the local area containing the sheet and the
background it makes inactive. Its extent comes from the container that lays out
the portal. `BottomSheetProvider` supplies the portal host but adds no native
container of its own, so its children alone do not define that area's bounds.
Use a layout container for each intended panel; nesting providers or sheet
declarations in JSX alone does not create separate presentation areas. Sheets
rendered by the same portal host form a stack in one context.

Independent panels keep their own background isolated, even when they share a
React Native root or window. Selecting one panel for input does not release
another panel's isolation. When presentation areas are physically nested, the
inner area's restrictions combine with those of the enclosing area; the inner
portal does not take over background outside its own area.

## Android close requests

`onCloseRequest` is **Android and web only**. Android system Back, a committed
predictive Back gesture, and a complete, unmodified physical-keyboard Escape
press use the same close request callback. The callback reports the request but
does not change the controlled `index`, choose a detent, or dismiss the sheet.
The consumer decides whether and how to close it.

To close a sheet in response, update `index` to a zero-height detent:

```tsx
const [index, setIndex] = useState(1);

<ModalBottomSheet
  detents={[0, 400]}
  index={index}
  onIndexChange={setIndex}
  onCloseRequest={() => setIndex(0)}
>
  {/* content */}
</ModalBottomSheet>;
```

### Input behavior

The callback runs after a regular Back action or predictive Back commit.
Predictive gesture progress does not animate the sheet, and cancelling the
gesture does not invoke the callback. Escape emits once for a completed,
unmodified physical-key press; modified, repeated, incomplete, or cancelled
sequences do not emit additional requests.

Each fresh input selects its context from current focus and presentation state.
Once predictive Back or an Escape press captures an owner, changing focus or
context does not transfer that sequence to another sheet or the host.

A sheet selected for Back/Escape while visibly animating to a closed target
consumes input without another callback until the animation settles, provided it
has a handler. After settle, fresh input resolves its context again. A no-op
handler likewise consumes eligible input while leaving the sheet open.

### Input context

A foreground `nativeOverlay` uses a window-wide input context regardless of
focus in underlying portal panels. Otherwise, portals select a local context
before applying presentation ordering.

Recognized current accessibility focus takes priority. Keyboard focus is
considered only after the absence of accessibility focus is confirmed. Touching
another panel does not by itself replace focus. For nested areas, input selects
the innermost context that contains the focus and has an active presentation. An
inner context without an active presentation does not displace its enclosing
active context.

Focus known to be outside all portal contexts leaves Back and Escape to the
host's normal input handling. When focus is absent or cannot be resolved
reliably, the existing window input fallback selects the frontmost active
portal, or a deterministic close fallback owner if visual order is unresolved.
This fallback does not assign focus or expand the selected portal's isolation
area.

For independent panels A and B, each with an active portal and an
`onCloseRequest` handler, with B visually above A:

| Current focus                        | Fresh Back/Escape target                                         |
| ------------------------------------ | ---------------------------------------------------------------- |
| Recognized focus in A                | A's local top presentation, despite B's higher position          |
| Recognized focus outside both panels | Normal host handling                                             |
| Absent or unresolved focus           | Window input fallback: B when its visual priority is established |

### Presentation ordering

Within the selected portal context, the topmost active presentation receives the
close request. If visual order cannot establish a unique top presentation, a
deterministic close fallback owner is used. That choice only routes close input;
it does not establish a screen reader top presentation or widen isolation.

A portal whose target is initially unresolved, already settled at zero height,
or closed without a visible animation is skipped. A portal that is visibly
animating closed remains active until settle, so a lower portal in that context
is not promoted early.

If the selected presentation has no `onCloseRequest`, Back uses normal host
handling and Escape remains in normal key routing. The library does not search
for a handler in a lower sheet, an enclosing context, or another panel. This
also applies while the selected presentation remains visibly closing.

On Android, `nativeOverlay` is hosted in a separate dialog window and does not
participate in portal ordering. Without a handler it forwards Back to normal
host handling and leaves Escape in normal key routing, while retaining its
window-modal scope.

### Target eligibility

Eligibility is based on the resolved native target height, not the detent index
or current animated position. Numeric `0`, `0%`, and `programmatic(0)` are
closed targets. A `content` target becomes eligible only after measurement
resolves it above zero. A sheet with no zero-height detent, such as
`detents={[300, 600]}`, remains eligible at every target; the consumer can
unmount it or change its detents if the close request should make it disappear.

### Limitations

An inconclusive accessibility-focus read, including a null result from a virtual
focus query, does not confirm that accessibility focus is absent. It uses the
window input fallback instead of substituting keyboard focus. TalkBack may be
reading panel A while that fallback selects panel B; not every virtual focus can
be recognized reliably.

A focused control can consume Escape before portal fallback sees it. When the
window fallback applies and keyboard focus is outside the portal tree, delivery
is best effort. Use `nativeOverlay` with `onCloseRequest` when Escape must be
owned by a separate window.

On Android API 24–27, this key-delivery fallback is supported for standard React
Native and AndroidX hosts based on `ReactActivity`, `AppCompatActivity`, or
`ComponentActivity`. Custom hosts and custom window callbacks can intercept key
events before the portal receives them.

Inline `BottomSheet`, iOS physical-keyboard Escape, accessibility dismiss
actions, scrim taps, drag gestures, and programmatic index changes are outside
this callback and keep their existing behavior.

## Accessible dismissal

An available accessibility dismiss action directly selects an eligible
non-programmatic closed detent without invoking `onCloseRequest`. On iOS,
VoiceOver Escape uses the action's local presentation context. Its top
presentation may attempt dismissal and consumes the gesture even when dismissal
is unavailable. If the local context or top presentation cannot be resolved, the
gesture continues through normal UIKit routing.

When an iOS sheet fills its host, there is no outside-sheet area for the Dismiss
control, so that control is unavailable. VoiceOver Escape can still close it
when an eligible non-programmatic closed detent is available.

## Screen reader transitions

For portal modals, the previous screen reader interface remains available while
the sheet opens. After opening settles, the sheet content becomes available and
the background in its presentation context is excluded from screen reader
navigation. During closing, that accessible interface is retained until the
sheet is fully closed. A new sheet that closes before finishing its opening is
never exposed to the screen reader.

This transition timing applies to portals. `nativeOverlay` uses the window
boundary described below.

Isolation updates follow React Native mounting and the library's presentation
lifecycle. Direct hierarchy or accessibility-property changes by other native
code do not have guaranteed automatic refresh. Independent panels that partly
overlap do not have a guarantee that every exposed portion remains accessible.
The handoff does not guarantee a fixed screen reader response time.

## Native overlay

By default `ModalBottomSheet` renders through `BottomSheetProvider`’s portal.
That portal lives in your React tree, so a sheet opened from a screen presented
as a native modal (for example, a React Navigation native-stack screen with
`presentation: 'modal'`) is confined to that screen and cannot cover it.

Set `nativeOverlay` to present the sheet in a native overlay above
everything—including native modal screens—so it always covers the full window.
On iOS, a `UIWindow`-attached container is used; on Android, a full-screen,
edge-to-edge, transparent dialog; on the web, a fixed-position layer in
`document.body`.

The overlay keeps the background of its window presentation inactive for touch
and accessibility while the sheet is visibly open or closing. A transparent
scrim, an absent or programmatic-only closed detent, and an omitted
`onCloseRequest` handler do not make that background interactive. Sheet content
remains usable; normal background interaction resumes after closed settle or
removal. Scrim taps and accessibility dismissal still require an eligible
non-programmatic closed detent.

```tsx
<ModalBottomSheet
  nativeOverlay
  index={index}
  onIndexChange={setIndex}
  surface={/* ... */}
>
  {/* ... */}
</ModalBottomSheet>
```

## React context

`BottomSheetProvider`’s portal renders the sheet’s content inside
`BottomSheetProvider`, not where `ModalBottomSheet` appears in your tree.
Content inside the sheet can read context from providers above
`BottomSheetProvider`, but not from providers between `BottomSheetProvider` and
the sheet. This also applies to navigation context: With `BottomSheetProvider`
at the app root, `useNavigation()` inside the sheet does not see the screen that
opened it.

```tsx
<ThemeContext.Provider value={theme}>
  {/* Available inside sheets. */}
  <BottomSheetProvider>
    <UserContext.Provider value={user}>
      {/* Not available inside sheets. */}
      <Screen />
    </UserContext.Provider>
  </BottomSheetProvider>
</ThemeContext.Provider>
```

When a provider cannot move above `BottomSheetProvider`, read the value in the
component that renders the sheet and provide it again inside the sheet:

```tsx
const SheetOwner = () => {
  const user = useContext(UserContext);
  const [index, setIndex] = useState(0);

  return (
    <ModalBottomSheet
      index={index}
      onIndexChange={setIndex}
      surface={/* ... */}
    >
      <UserContext.Provider value={user}>
        <SheetContent />
      </UserContext.Provider>
    </ModalBottomSheet>
  );
};
```

The sheet stays in sync: When the value changes, `SheetOwner` re-renders and
passes the updated content to the portal.

Navigation context is internal to the navigation library, so pass what the sheet
needs instead: Call `useNavigation()` in `SheetOwner` and hand the sheet content
props or callbacks, such as `onSelect={() => navigation.goBack()}`.

With `nativeOverlay`, the sheet stays where it is rendered in the React tree and
is moved natively, so it reads context from every provider above it.
