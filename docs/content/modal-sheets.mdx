# Modal sheets

`ModalBottomSheet` renders above other content with an optional scrim
(transparent by default).

```tsx
const [index, setIndex] = useState(0);
const insets = useSafeAreaInsets();
```

```tsx
<ModalBottomSheet
  index={index}
  onIndexChange={setIndex}
  surface={
    <View style={[StyleSheet.absoluteFill, { backgroundColor: 'white' }]} />
  }
>
  <View style={{ padding: 16, paddingBottom: insets.bottom + 16 }}>
    <Text>Sheet content</Text>
  </View>
</ModalBottomSheet>
```

## Scrim

Tapping the scrim collapses the sheet to the closed detent. Use `scrimColor` to
customize the scrim color:

```tsx
<ModalBottomSheet
  index={index}
  onIndexChange={setIndex}
  surface={/* ... */}
  scrimColor="rgba(0, 0, 0, 0.3)"
>
  {/* ... */}
</ModalBottomSheet>
```

By default, the scrim fades in as the sheet opens and then holds at full
opacity, so detents above the first share the same scrim. Use `scrimOpacities`
to control the opacity at each detent: It takes one value in 0–1 per detent,
indexed to match `detents`, and interpolates linearly as the sheet is dragged
between them. A shorter array reuses its last value for any remaining detents.

The default maps each detent to 0 when it is closed and 1 otherwise, so the
scrim is transparent at any closed detent and fully opaque at every open one.

To keep the scrim deepening across every detent, pass one value per detent:

```tsx
<ModalBottomSheet
  index={index}
  onIndexChange={setIndex}
  detents={[0, 300, 'content']}
  scrimColor="rgba(0, 0, 0, 0.3)"
  scrimOpacities={[0, 0.5, 1]}
  surface={/* ... */}
>
  {/* ... */}
</ModalBottomSheet>
```

## Android close requests

`onRequestClose` is **Android only**. When the sheet is open, Android system
Back and a committed predictive Back gesture invoke the callback. A complete,
unmodified physical-keyboard Escape press uses the same request path. In portal
mode, an eligible sheet intercepts Escape before a focused descendant in its own
subtree. When focus is outside that subtree, AndroidX provides a non-invasive
fallback after normal key routing leaves Escape unhandled. A `nativeOverlay`
owns its dialog window and therefore provides guaranteed Escape handling.

`onRequestClose` is emitted only after a predictive Back gesture commits.
Gesture progress does not currently animate the sheet, and cancelling the
gesture does not invoke the callback. A portal registers its request-close Back
callback lazily: no native callback is added until `onRequestClose` is first
provided for the resolved host. After that first installation, the portal keeps
the callback for the host's structural lifetime and changes only its enabled
state when eligibility changes, following Android’s
[predictive Back callback best practices](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture#callback-best-practices).
If eligibility is lost after a predictive gesture selects that callback but
before commit, the commit completes as a no-op; it is not re-dispatched to
navigation.

Escape is claimed on its initial key-down and emits once on the matching key-up
when a request handler is eligible. A `nativeOverlay` claims an unmodified
Escape even without a handler, and keeps the sequence until its terminal key-up.
Holding the key does not emit repeated requests. A cancelled key-up, a key-up
with modifiers, or a press that never completes does not emit a request. A
modified press or one that starts while the sheet is ineligible is not claimed.

A portal installs one stable AndroidX unhandled-key listener lazily when
`onRequestClose` first appears, then keeps it for that host's structural
lifetime. When focus is inside the eligible portal subtree, the portal claims
Escape before the focused child receives it. With focus elsewhere, focused views
receive Escape through normal dispatch first; if one consumes it, the portal
does not emit a close request. This is why external-focus portal Escape is best
effort and `nativeOverlay` is required when Escape must be intercepted. The
generic AndroidX
[`ViewCompat.addOnUnhandledKeyEventListener`](<https://developer.android.com/reference/androidx/core/view/ViewCompat#addOnUnhandledKeyEventListener(android.view.View,androidx.core.view.ViewCompat.OnUnhandledKeyEventListenerCompat)>)
API documents the underlying unhandled-key contract.

On API 24–27, AndroidX delivers the external-focus fallback for the standard
React Native hosts based on `ReactActivity`, `AppCompatActivity`, or
`ComponentActivity`. A plain `Activity` still supports local interception when
focus is inside the portal, but its external-focus fallback is not guaranteed on
those versions. On API 28 and newer, Android supplies the platform unhandled-key
listener. A custom `Window.Callback` that consumes an event before delegating it
to the view hierarchy can preempt both portal mechanisms. The library never
replaces or restores the window callback.

The input transport depends on how the sheet is presented. A portal sheet uses
the nearest valid `OnBackPressedDispatcherOwner` published in its Android view
tree, or a current host Activity that both owns the attached portal hierarchy
and is not finishing or destroyed. Back is registered only when that dispatcher
also has a resolved lifecycle. While the sheet is eligible, its native callback
consumes Back before React Native emits a `hardwareBackPress` event to its
JavaScript `BackHandler`. A plain `Activity` does not implement
`OnBackPressedDispatcherOwner`, so it supports local portal Escape but not
portal Back; its external-focus Escape fallback follows the API limitations
above. A portal without `onRequestClose` does not add either native
registration. A `nativeOverlay` has a separate window and therefore handles Back
through its dialog dispatcher.

Portal Escape handling is resolved independently from the Back dispatcher. The
listener is attached directly to the portal `BottomSheetView`, while Activity
ownership checks remain in host resolution for Back and lifecycle safety. This
also lets a custom owner nested under a `ComponentDialog` keep Back on its
custom dispatcher while Escape follows normal dispatch in the dialog's view
hierarchy. A `nativeOverlay` handles Escape through its dialog window's key
listener.

A portal claims new Back or Escape input only while its resolved lifecycle is
`RESUMED`. The nearest view-tree lifecycle is used by default. When a custom
dispatcher is nested below only a broader Activity or `ComponentDialog`
lifecycle, the dispatcher’s own lifecycle is used instead. Pausing that owner
disables Back and makes its stable Escape listener passive for new presses. An
Escape press that began while `RESUMED` remains consumed through its terminal
key-up, but does not emit `onRequestClose` if the lifecycle paused in the
meantime. Closing the target, removing the handler, or losing topmost status
changes eligibility without reordering registrations that were already
installed. Structural boundaries — `modal={false}`, switching to
`nativeOverlay`, detach/destroy, presentation failure, or a host change — remove
those registrations and reset the lazy lifetime. It is not carried to a new host
when no handler is present there. When no lifecycle exists, the React host’s
active state is used as a limited eligibility fallback for Escape; Back still
requires both a dispatcher and lifecycle. A destroyed custom owner never falls
back to a broader Activity lifecycle.

This host resolution is supported for standard AndroidX hosts
(`ComponentActivity`, `ComponentDialog`, and their subclasses) and custom owners
nested under those hosts’ root views. A custom host that owns a separate,
non-`ComponentDialog` window is outside this guaranteed scope.

The `RESUMED` check is a best-effort safeguard. A `BottomSheetProvider` mounted
at an Activity root can observe only that Activity’s lifecycle, not the
lifecycle of the screen that originally opened a portal. Screen-level providers
should therefore publish the appropriate owners and close or unmount their
sheets when the screen blurs.

When multiple portal sheets stay mounted, `BottomSheetProvider` coordinates
their visual stack. Only the last open portal in render order can enable its
Back/Escape request-close callback. A portal below another open portal keeps its
callback inactive, even if the lower portal was reopened most recently. The
topmost portal participates in this ordering whether or not it has an
`onRequestClose` handler: if it has none, Back propagates to the remaining
dispatcher callbacks and Escape remains unclaimed instead of invoking a lower
sheet’s handler. `nativeOverlay` uses its separate native window and does not
participate in this portal coordination. An open `nativeOverlay` owns Android
Back and unmodified Escape regardless of whether `onRequestClose` is provided.
Without a handler it consumes the request without changing the sheet, so it also
blocks `BackHandler`, modal callbacks, navigation, and portals below it. The
provider-level topmost guarantee extends only to the sheets that provider
coordinates. Across independent providers and external native Back callbacks,
[`OnBackPressedDispatcher`](https://developer.android.com/reference/androidx/activity/OnBackPressedDispatcher)
uses LIFO order: the enabled callback added most recently receives Back first.
Once installed, closing and reopening a sheet or temporarily removing its
handler changes only its stable callback's enabled state, so it does not change
that registration order.

When a portal is ineligible, Back continues through the remaining dispatcher
callbacks to navigation, React Native’s `BackHandler`, or the Activity’s default
behavior. A `nativeOverlay` remains the owner while its open target is visible
or while its closing animation/gesture is still interactive. Its events are
consumed until that visual interaction ends; they are then released so the next
Back can reach the portal, navigation, or Activity below. Predictive Back
requests are emitted only after commit, and a cancelled gesture emits nothing.

The callback is a controlled request, not a native dismissal. The sheet does not
change its index, choose a detent, use the scrim-dismiss path, or dismiss a
`nativeOverlay` dialog. To close it, update your controlled `index` to a
zero-height detent:

```tsx
const [index, setIndex] = useState(1);

<ModalBottomSheet
  detents={[0, 400]}
  index={index}
  onIndexChange={setIndex}
  onRequestClose={() => setIndex(0)}
>
  {/* content */}
</ModalBottomSheet>;
```

With this setup, the first Back closes the sheet without leaving the current
screen. The overlay continues consuming Back during the closing animation; after
it finishes, the next Back continues through the remaining Activity callbacks.
Reopening the sheet enables the request-close callback again.

A no-op handler consumes a qualifying Back or Escape request and leaves the
sheet open:

```tsx
<ModalBottomSheet
  detents={[0, 400]}
  index={index}
  onRequestClose={() => {
    // Confirm with the user, or intentionally keep the sheet open.
  }}
>
  {/* ... */}
</ModalBottomSheet>
```

Close-request eligibility in both presentation modes is based on the resolved
native target, not its index or the sheet’s animated position. This means
`index={0}` remains eligible for `detents={[300, 600]}`. Targets that resolve to
zero—including numeric `0`, `0%`, and `programmatic(0)`—are closed. A `content`
target becomes eligible after its content is measured and resolves to a height
greater than zero. While the view is detached, no close request is emitted and
its native input handlers are removed until it reattaches. While the attached
target is not yet resolved, a portal leaves Back and Escape unclaimed, while a
`nativeOverlay` consumes Back and Escape once it is visible or interactive. A
sheet whose detents all resolve to a nonzero height remains eligible at every
resolved target:

```tsx
<ModalBottomSheet
  detents={[300, 600]}
  index={index}
  onRequestClose={() => {
    // There is no closed detent. Unmount the sheet or replace the detents if
    // this request should make it disappear.
  }}
>
  {/* ... */}
</ModalBottomSheet>
```

When `onRequestClose` is omitted, a portal keeps its existing pass-through
behavior. An open `nativeOverlay` instead consumes Back and unmodified Escape
without closing the dialog; the consumer must unmount it or change its
controlled target if it should disappear.

Scrim taps, drag dismissal, accessibility dismiss actions, and programmatic
index changes keep their existing independent behavior and do not invoke this
callback. iOS physical-keyboard Escape, `accessibilityPerformEscape`, and inline
`BottomSheet` are outside this API.

## Native overlay

By default `ModalBottomSheet` renders through `BottomSheetProvider`’s portal.
That portal lives in your React tree, so a sheet opened from a screen presented
as a native modal (for example, a React Navigation native-stack screen with
`presentation: 'modal'`) is confined to that screen and cannot cover it.

Set `nativeOverlay` to present the sheet in a native overlay above
everything—including native modal screens—so it always covers the full window.
On iOS, a `UIWindow`-attached container is used; on Android, a full-screen,
edge-to-edge, transparent dialog.

```tsx
<ModalBottomSheet
  nativeOverlay
  index={index}
  onIndexChange={setIndex}
  surface={/* ... */}
>
  {/* ... */}
</ModalBottomSheet>
```
