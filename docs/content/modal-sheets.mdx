# Modal sheets

`ModalBottomSheet` renders above other content with an optional scrim
(transparent by default).

```tsx
const [index, setIndex] = useState(0);
const insets = useSafeAreaInsets();
```

```tsx
<ModalBottomSheet
  index={index}
  onIndexChange={setIndex}
  surface={
    <View style={[StyleSheet.absoluteFill, { backgroundColor: 'white' }]} />
  }
>
  <View style={{ padding: 16, paddingBottom: insets.bottom + 16 }}>
    <Text>Sheet content</Text>
  </View>
</ModalBottomSheet>
```

## Scrim

Tapping the scrim collapses the sheet to the closed detent. Use `scrimColor` to
customize the scrim color:

```tsx
<ModalBottomSheet
  index={index}
  onIndexChange={setIndex}
  surface={/* ... */}
  scrimColor="rgba(0, 0, 0, 0.3)"
>
  {/* ... */}
</ModalBottomSheet>
```

By default, the scrim fades in as the sheet opens and then holds at full
opacity, so detents above the first share the same scrim. Use `scrimOpacities`
to control the opacity at each detent: It takes one value in 0–1 per detent,
indexed to match `detents`, and interpolates linearly as the sheet is dragged
between them. A shorter array reuses its last value for any remaining detents.

The default maps each detent to 0 when it is closed and 1 otherwise, so the
scrim is transparent at any closed detent and fully opaque at every open one.

To keep the scrim deepening across every detent, pass one value per detent:

```tsx
<ModalBottomSheet
  index={index}
  onIndexChange={setIndex}
  detents={[0, 300, 'content']}
  scrimColor="rgba(0, 0, 0, 0.3)"
  scrimOpacities={[0, 0.5, 1]}
  surface={/* ... */}
>
  {/* ... */}
</ModalBottomSheet>
```

## Android close requests

`onRequestClose` is **Android only**. When the sheet's resolved target height is
greater than zero, Android system Back and a committed predictive Back gesture
can invoke the callback. A complete, unmodified physical-keyboard Escape press
uses the same request path. The callback only reports the request: the consumer
still decides whether and how to change the controlled target. This matches the
modal effect of React Native `Modal`: close input is intercepted and reported
instead of choosing a dismissal for the consumer. The Android transports are not
intended to be identical event-for-event.

Portal sheets that share the same Android `rootView` form one native ownership
stack, including sheets rendered by independent `BottomSheetProvider` instances.
Membership order is structural. The highest membership whose target is resolved
above zero and whose lifecycle is `RESUMED` owns Back/Escape. Unresolved,
zero-height, `PAUSED`, and `STOPPED` portals are skipped, so the next qualifying
portal below can handle new requests. Resuming a portal restores its previous
position instead of moving it to the top. Closing, reopening, measuring content,
and toggling a handler likewise do not reorder existing memberships.

`onRequestClose` is emitted only after a predictive Back gesture commits.
Gesture progress does not currently animate the sheet, and cancelling the
gesture does not invoke the callback. Every attached portal registers
lightweight root membership, even if it has no handler. Its platform Back
callback and unhandled-key listener are installed lazily only after
`onRequestClose` first appears for that structural host. They then remain stable
across open/close, ownership, handler, pause/resume, and lifecycle-owner
`DESTROYED` updates. Back changes only the callback's enabled state, following
Android’s
[predictive Back callback best practices](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture#callback-best-practices).
If ownership, the handler, the active lifecycle, or the open target is lost
after a predictive gesture selects that callback but before commit, the commit
completes as a no-op. It is not re-dispatched to a new owner or navigation; the
next Back uses the then-current owner.

For Escape, the coordinator pins an initial unmodified key-down to the current
owner. Repeats and the terminal key-up stay with that same membership even if
ownership changes. Losing ownership, the handler, active lifecycle, or the open
target before key-up consumes an already claimed sequence without emitting and
without transferring it. Holding the key does not emit repeated requests. A
cancelled key-up, a key-up with modifiers, or a press that never completes does
not emit a request. Modified presses and presses whose owner cannot handle the
request are not claimed.

Every local and unhandled-key portal path delegates to the same root
coordinator. With focus inside any portal subtree in the root, an eligible owner
with a handler claims the complete Escape sequence before the focused
descendant, so that descendant cannot consume either key-down or key-up. If the
owner has no handler, the portal leaves Escape unhandled and normal descendant
dispatch can consume it; the request never falls through to a lower portal. With
`onRequestClose`, `nativeOverlay` enforces the same modal priority through its
separate dialog key listener. Without a handler, it does not claim Escape.

With focus outside all portal subtrees, focused views receive Escape through
normal dispatch first; if one consumes it, the portal group does not emit a
close request. Portal Escape from outside those subtrees is therefore best
effort. Use `nativeOverlay` with `onRequestClose` when Escape must be owned by a
separate dialog window. The generic AndroidX
[`ViewCompat.addOnUnhandledKeyEventListener`](<https://developer.android.com/reference/androidx/core/view/ViewCompat#addOnUnhandledKeyEventListener(android.view.View,androidx.core.view.ViewCompat.OnUnhandledKeyEventListenerCompat)>)
API documents the underlying unhandled-key contract.

On API 24–27, AndroidX delivers the external-focus fallback for the standard
React Native hosts based on `ReactActivity`, `AppCompatActivity`, or
`ComponentActivity`. A plain `Activity` still supports local interception when
focus is inside the portal, but its external-focus fallback is not guaranteed on
those versions. On API 28 and newer, Android supplies the platform unhandled-key
listener. A custom `Window.Callback` that consumes an event before delegating it
to the view hierarchy can preempt both portal mechanisms. The library never
replaces or restores the window callback.

The input transport depends on how the sheet is presented. A portal sheet uses
the nearest valid `OnBackPressedDispatcherOwner` published in its Android view
tree, or a current host Activity that both owns the attached portal hierarchy
and is not finishing or destroyed. Back is registered only when that dispatcher
also has a resolved lifecycle. While the sheet is eligible, its native callback
consumes Back before React Native emits a `hardwareBackPress` event to its
JavaScript `BackHandler`. A plain `Activity` does not implement
`OnBackPressedDispatcherOwner`, so it supports local portal Escape but not
portal Back; its external-focus Escape fallback follows the API limitations
above. A portal whose structural host has never had `onRequestClose` adds only
root membership, not a Back callback or key listener. A `nativeOverlay` has a
separate window and therefore handles Back through its dialog dispatcher.

Portal Escape handling is resolved independently from the Back dispatcher. Each
listener is attached directly to its portal `BottomSheetView` and delegates to
the coordinator for that exact `rootView`, while Activity ownership checks
remain in host resolution for Back and lifecycle safety. This also lets a custom
owner nested under a `ComponentDialog` keep Back on its custom dispatcher while
Escape follows normal dispatch in the dialog's view hierarchy. A `nativeOverlay`
handles Escape through its dialog window's key listener.

A portal can handle new Back or Escape input only while its resolved lifecycle
is `RESUMED`. The nearest view-tree lifecycle is used by default. When a custom
dispatcher is nested below only a broader Activity or `ComponentDialog`
lifecycle, the dispatcher’s own lifecycle is used instead. Pausing or destroying
that owner temporarily excludes the portal from ownership, allowing the next
qualifying membership below to handle new requests. `RESUMED` restores the
portal's earlier structural position. A destroyed custom owner stays excluded
and never falls back to a broader Activity lifecycle. Lifecycle-owner
`DESTROYED` does not by itself mean that `BottomSheetView.destroy()` ran, so an
already-installed transport remains present but disabled until structural
integration ends.

Changing dispatcher or lifecycle host within the same root preserves membership
position but replaces that host's platform integration. Detach, component
destroy, `modal={false}`, switching between portal and `nativeOverlay`,
presentation failure, or migration to another root removes membership and the
platform integration. Reattachment in a root creates a new position. A handler
lifetime is not carried to a new root when no handler is present there. When no
lifecycle exists, the React host’s active state is used as a limited eligibility
fallback for Escape; Back still requires a dispatcher.

This host resolution is supported for standard AndroidX hosts
(`ComponentActivity`, `ComponentDialog`, and their subclasses) and custom owners
nested under those hosts’ root views. A custom host that owns a separate,
non-`ComponentDialog` window is outside this guaranteed scope.

The `RESUMED` check is a best-effort safeguard. A `BottomSheetProvider` mounted
at an Activity root can observe only that Activity’s lifecycle, not the
lifecycle of the screen that originally opened a portal. Screen-level providers
should therefore publish the appropriate owners and close or unmount their
sheets when the screen blurs.

An active open portal owner participates whether or not it can handle requests.
If it has no handler, all lower portal callbacks remain disabled: Back can
continue to an external dispatcher callback, navigation, `BackHandler`, or
Activity behavior, while Escape remains unhandled. It never falls through to a
lower sheet merely because the owner cannot emit. An inactive lifecycle instead
removes that portal from current ownership without changing its membership
order.

`nativeOverlay` uses its separate native window and does not participate in root
portal coordination. Providing `onRequestClose` gives an open `nativeOverlay`
modal ownership of Android Back and unmodified Escape. Once the consumer starts
closing the sheet, the dialog keeps that boundary while it remains visible or
interactive: further Back and Escape input is consumed without a second
callback. After the closing animation finishes, the Activity receives Back
again. If a captured Escape press loses its handler, modal state, active
lifecycle, or open target, that loss is terminal for the current sequence:
repeats and key-up remain consumed without a callback even if eligibility is
restored. The next key-down uses the restored state.

Without `onRequestClose`, `nativeOverlay` preserves its legacy pass-through
behavior. Back is forwarded to the exact host `ComponentActivity` dispatcher
associated with the dialog, including while the sheet is closing, and Escape
stays in normal key routing. A focused descendant can therefore receive the full
Escape sequence. Forwarding goes directly to the Activity; it is not offered to
another `nativeOverlay` dialog below.

The dialog keeps one Back callback registered for its structural lifetime. A
predictive gesture pins its complete action at start: request close, consume, or
forward to that host Activity dispatcher. Adding a handler does not retarget an
already-started forwarding action. If a request-close action loses the handler,
modal state, active lifecycle, or open target before commit, that gesture
finishes as a consumed no-op even if eligibility returns; the next Back uses the
new state.

When no open portal owns the root, its stable callbacks are disabled and Back
continues through the dispatcher. Predictive Back requests are emitted only
after commit, and a cancelled gesture emits nothing.

The callback is a controlled request, not a native dismissal. The sheet does not
change its index, choose a detent, use the scrim-dismiss path, or dismiss a
`nativeOverlay` dialog. To close it, update your controlled `index` to a
zero-height detent:

```tsx
const [index, setIndex] = useState(1);

<ModalBottomSheet
  detents={[0, 400]}
  index={index}
  onIndexChange={setIndex}
  onRequestClose={() => setIndex(0)}
>
  {/* content */}
</ModalBottomSheet>;
```

With this setup, the first Back closes the sheet without leaving the current
screen. The overlay continues consuming Back during the closing animation; after
it finishes, the next Back continues through the remaining Activity callbacks.
Reopening the sheet enables the request-close callback again.

A no-op handler consumes a qualifying Back or Escape request and leaves the
sheet open:

```tsx
<ModalBottomSheet
  detents={[0, 400]}
  index={index}
  onRequestClose={() => {
    // Confirm with the user, or intentionally keep the sheet open.
  }}
>
  {/* ... */}
</ModalBottomSheet>
```

Because an eligible sheet has modal priority over focused descendants, a control
with transient state can handle the request in the sheet callback. For example,
close an open dropdown first and close the sheet on a later request:

```tsx
const handleRequestClose = () => {
  if (dropdownOpen) {
    setDropdownOpen(false);
    return;
  }

  setIndex(0);
};

<ModalBottomSheet
  index={index}
  onIndexChange={setIndex}
  onRequestClose={handleRequestClose}
>
  {/* content with the dropdown */}
</ModalBottomSheet>;
```

Close-request eligibility in both presentation modes is based on the resolved
native target, not its index or the sheet’s animated position. This means
`index={0}` remains eligible for `detents={[300, 600]}`. Targets that resolve to
zero—including numeric `0`, `0%`, and `programmatic(0)`—are closed. A `content`
target can own requests only after its content is measured and resolves to a
height greater than zero. While the view is detached, no close request is
emitted and its native membership and input handlers are removed. An attached
portal whose target is unresolved or zero is skipped in favor of the highest
open portal below it; if none exists, portal Back/Escape are left unclaimed. A
`nativeOverlay` with a handler continues consuming Back and Escape while a
closed target is still animating, without emitting another request. Once the
animation finishes it releases close input. Without a handler it forwards Back
and leaves Escape unclaimed throughout. A sheet whose detents all resolve to a
nonzero height remains eligible at every resolved target:

```tsx
<ModalBottomSheet
  detents={[300, 600]}
  index={index}
  onRequestClose={() => {
    // There is no closed detent. Unmount the sheet or replace the detents if
    // this request should make it disappear.
  }}
>
  {/* ... */}
</ModalBottomSheet>
```

When `onRequestClose` is omitted, an open portal owns its root position but
cannot handle the request: it blocks lower portals, lets Back continue outside
the portal group, and leaves Escape for normal descendant dispatch. An open
`nativeOverlay` likewise emits no request. It forwards Back to the host Activity
and leaves unmodified Escape in normal routing, including for focused
descendants and while a controlled close is animating.

Scrim taps, drag dismissal, accessibility dismiss actions, and programmatic
index changes keep their existing independent behavior and do not invoke this
callback. iOS physical-keyboard Escape, `accessibilityPerformEscape`, and inline
`BottomSheet` are outside this API.

## Native overlay

By default `ModalBottomSheet` renders through `BottomSheetProvider`’s portal.
That portal lives in your React tree, so a sheet opened from a screen presented
as a native modal (for example, a React Navigation native-stack screen with
`presentation: 'modal'`) is confined to that screen and cannot cover it.

Set `nativeOverlay` to present the sheet in a native overlay above
everything—including native modal screens—so it always covers the full window.
On iOS, a `UIWindow`-attached container is used; on Android, a full-screen,
edge-to-edge, transparent dialog.

```tsx
<ModalBottomSheet
  nativeOverlay
  index={index}
  onIndexChange={setIndex}
  surface={/* ... */}
>
  {/* ... */}
</ModalBottomSheet>
```
